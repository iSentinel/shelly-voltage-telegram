# Issues 340/422/431: explicit dual OCI Cosign preflight

Date: 2026-11-19, Europe/Kyiv
Status: source-only QA; production release NOT activated

## Reason for change

The prior offline paired-rescue preflight verified full synthetic
L1/L2/L3/WAL/PHOTO rescue parity and the old/new source/OCI version
identities. Its output explicitly said that neither OCI signature
was verified. This evidence is insufficient to approve any real
update or rollback.

The candidate scripts/qa-paired-rescue-preflight.py now accepts
an explicit --verify-signatures flag. It performs the same mandatory
read-only database and source/OCI receipt checks before attempting
a network verification of both immutable OCI digests.

The verification requires:
- /usr/local/bin/cosign as a regular root-owned executable under
  trusted, non-group/world-writable parent directories.
- Actual installed Cosign version 3 or newer.
- Exact old and new sha256 digests, no mutable tags.
- cosign verify success against the exact immutable reference with
  the expected iSentinel/shelly-voltage-telegram GitHub Actions
  image.yml@refs/tags/v<version> certificate identity and
  https://token.actions.githubusercontent.com OIDC issuer.
- Separate successful verification for both the old and new image.
  Missing Cosign, incorrect version, an invalid digest, changed old
  receipt, a rejected signature or timeout blocks the entire proof.

Even two valid OCI signatures cannot authorize a release: the tool
remains --qa-only, its result always sets release_authorized=false
and rollback_authorized=false, and the newest production database is
never replaced. A verified image signature alone does not sign a
source archive or attest exact source-to-image byte correspondence.
